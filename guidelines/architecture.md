# Архитектура приложения

STG — локальный Go-фреймворк на `go.uber.org/fx`. Общие соглашения для разработки
и проверки изменений описаны в [AGENTS.md](../AGENTS.md).

## Framework и приложение

- `pkg/` — инфраструктурные модули: серверы, соединения, логирование, телеметрия,
  конфигурация и управление жизненным циклом. Импорты — `stg/pkg/...`.
- `internal/app/` — приложение и рабочие примеры todo, MAX-бота, авторизации и S3.
- `cmd/` — точки входа; флаг `-c` выбирает конфигурационный файл. После
  `create.sh` entry point находится в `cmd/app/`.

Изменяйте `pkg/`, когда задача требует изменения фреймворка; проверяйте его
потребителей. Бизнес-поведение размещайте в `internal/app/`.

`create.sh` создаёт приложение с другим module name и удаляет часть примеров,
`tests/`, `testkit/`, deployment и CI. Импорты и имена приложения в документации
переименовываются; имена скиллов `stg-*` сохраняются. Примеры в этих гайдлайнах
описывают исходный STG: после генерации проверяйте наличие указанных компонентов.

## Слои и зависимости

Направление зависимостей: `router -> services -> repository/clients/infra`.

| Слой | Ответственность |
|---|---|
| `internal/app/domain` | Общие бизнес-модели и ожидаемые бизнес-ошибки |
| `internal/app/services` | Бизнес-правила и оркестрация |
| `internal/app/repository` | Прямой доступ к хранилищу |
| `internal/app/clients` | Взаимодействие с внешней системой |
| `internal/app/router/<feature>ctrl` | HTTP-контракт, валидация и ответы |
| Infrastructure package | Локальная техническая возможность без внешнего сервиса |

Потребитель объявляет локальный интерфейс зависимости. Его `fx.go` получает
конкретную реализацию через `fx.In` и возвращает интерфейс через `fx.Out`;
адаптер содержит присваивания полей. Модули провайдеров регистрируют конкретные
конструкторы. В исходном STG пример — `internal/app/services/todolist/fx.go`;
он удаляется при генерации нового приложения.

Для новых контекстов один репозиторий принадлежит одному сервису. В существующем
todo-примере `todorepo` используют bot и todolist; это исключение, а не образец
для новых контекстов. Между контекстами обращайтесь к сервисам через локальные
интерфейсы. Ожидаемые ошибки проверяйте через `errors.Is`, технические оборачивайте
с контекстом операции и не возвращайте их текст HTTP-клиенту.

Контроллер экспортируется как `router.Controller` в Fx-группу `controller`.
Контроллерные модули собираются на уровне приложения; сервисы и репозитории —
через свои layer-модули. `webhookctrl` делегирует vendor handler напрямую и
не является обычным бизнес-контроллером.

## Конфигурация и lifecycle

[Box](../internal/app/box.go) подключает базовые модули Grace, health, server,
info, HTTP client и telemetry. Остальные модули подключаются в
[internal/app/fx.go](../internal/app/fx.go). Конфигурацию загружает
[pkg/config](../pkg/config/config.go); дополнительные секции читают providers
соответствующих пакетов. Конструкторы получают обязательные зависимости от Fx.

- Именованные PostgreSQL pools: `postgres:`; отдельно read и write.
- Именованные Redis pools: `redis:`.
- BGTasker: `background.tasks`, а не `bgtasker.tasks`.
- Постоянно работающие сервисы реализуют `grace.Service` и экспортируются в
  Fx-группу `grace`. Их `Stop` отменяет работу и дожидается горутин.
- `subscriber` — единственный читатель MAX updates; сейчас вызывает bot.
  Текущий unbounded dispatch не является lifecycle-образцом для новых сервисов.

Не полагайтесь на порядок остановки Grace-сервисов: пул останавливает их
параллельно. Подробности: [Grace](grace.md), [BGTasker](bgtasker.md).

## Проверка изменений

Unit-тесты изолированы моками. Infrastructure-backed suites находятся в
`tests/integrations_*`, HTTP E2E — в `tests/e2e`.

`make test_unit` запускает `internal/...` с coverage и race detector. Для
изменений framework и test helpers нужны отдельные focused tests. Актуальная
матрица команд и ограничения CI: [Тестирование](integration-testing.md).
